## 第一章：架构哲学

### 1.1 三条铁律

**铁律一：卡片即文件夹**
每张卡牌是一个独立的文件目录，包含该卡的 DZ 源文件、编译后的 AST 数据、元数据、卡面预览图、专属素材。删除该目录 = 从系统中完全移除该卡牌，零残留、零孤儿引用、零级联破坏。

**铁律二：UI 即投影**
UI 层不做任何业务判断、不存储任何领域数据、不产生任何新状态。UI 层的唯一职责是将领域数据"投影"到屏幕上。如果在 UI 上需要一个按钮、一个标签、一个列表，那必须有一个对应的领域模块提供这些数据。UI 是影子，模块是实体。

**铁律三：接口是唯一通信语言**
任何两个模块之间，不允许直接 import 对方的实现代码。模块 A 使用模块 B 的能力，必须通过 B 对外暴露的接口（trait/interface）。模块不关心接口的"实现者是谁"——只要签名匹配，任何实现都可以在运行时注入。

### 1.2 三铁律推导出的设计

从三条铁律出发，整个架构自然呈现为：

```
                    ┌─ 接口层（契约） ─┐
                    │                  │
  接口调用方 ──────→│  接口定义(trait)  │←────── 接口实现方
  (消费者)          │                  │        (提供者)
                    └──────────────────┘
```

- 消费者只依赖接口签名，不知道实现方的存在
- 提供者实现接口，注册到模块注册表
- 初始化时由注册表完成消费者和提供者的绑定
- 替换实现方 = 替换接口的实现者，消费者代码一行不动

## 第二章：静态定义 vs 运行时实例

### 2.1 两张表的世界

整个系统存在两类完全不同的"卡牌"：

| | 静态卡牌定义 | 运行时卡牌实例 |
|---|---|---|
| 类比 | 蓝图/模板/类 | 实例/对象 |
| 唯一标识 | 编号，如 `JB01`（击敌） | 运行时 ID，如 `JB01_1` `JB01_2` … `JB01_12` |
| 存储位置 | `cards/JB01-击敌/` 目录 | 战场模块内存 + 存档文件 |
| 是否可变 | 否（设计师修改需走版本控制） | 是（HP、护甲、标记等随对局变化） |
| 数量 | 78 种（原始套） | 对局中动态产生，受配比限制 |
| 删除方式 | 删除 cards/ 下对应目录 | 对局结束释放内存；淘汰时移入坟场 |

### 2.2 运行时 ID 规则

```
规则：{静态编号}_{实例序号}

示例：
  JB01_1  击敌的第 1 张实体（牌堆中）
  JB01_2  击敌的第 2 张实体
  JB01_12 击敌的第 12 张实体

  GZ04_1  长剑的第 1 张实体（玩家 A 装备中）
  GZ04_2  长剑的第 2 张实体（玩家 B 装备中）

  BJ01_1  仁心标记在当前对局中第一次被放置时产生的实例
```

同一种静态卡牌可以在对局中同时存在多个实例（12 张击敌），它们共享同一份静态定义（`cards/JB01-击敌/card.json`），但各自维护独立的运行时状态（HP、标记、所在区域、当前效果栈）。

### 2.3 战场模块的核心职责

战场模块是运行时实例的管理中枢。它不参与卡牌设计，只负责对局中的资源调度：

```
战场模块 (Battlefield)

  ① 实例化
    对局初始化时，根据配比表从静态仓库逐个拉取定义
    → 产生带运行时 ID 的实例列表

  ② 区域管理
    手牌区 / 牌堆区 / 场上区 / 弃牌堆 / 坟场 / 放逐区
    每个区域是 {运行时 ID → 实例状态} 的映射

  ③ 状态变更
    实例的 HP、护甲、技力、标记、装备等随对局推进而变化
    战场模块是唯一有权修改实例状态的模块

  ④ 效果结算
    按书写的顺序串联支付→结算→连锁
    管理效果栈（谁先结算、谁被免疫、谁触发连锁）

  ⑤ 素材调度
    被动调用 AssetLoaderPort 获取卡面图片、图标等静态资源
    战场模块不存储素材，只计算"此刻应该显示哪个素材"
```

### 2.4 实例的生命周期

```
对局开始
  │
  ├─→ 战场模块读取配比表
  │     JB01 需要 12 个实例 → 产生 JB01_1 ~ JB01_12
  │     每个实例：{ id, static_def_ref, hp:0, armor:0, ... }
  │
  ├─→ 洗牌 → 实例进入牌堆区
  │
  ├─→ 抽牌 → 实例从牌堆区移动到玩家手牌区
  │
  ├─→ 打出 → 实例从手牌区移动到场上区 → 效果结算
  │
  ├─→ 被弃置/摧毁 → 实例从场上区移动到弃牌堆
  │
  ├─→ 被淘汰 → 实例进入坟场（不可复活）
  │
  └─→ 对局结束 → 所有实例从内存释放 → 存档保留最终状态快照
```

## 第三章：立体化模块布局

### 3.1 七层结构

```
┌─────────────────────────────────────────────────┐
│  L5  呈现层 (Presentation)                       │
│      React 组件树，纯投影。                       │
├─────────────────────────────────────────────────┤
│  L4  应用层 (Application)                        │
│      用例编排。hooks → useCase。                  │
├─────────────────────────────────────────────────┤
│  ───────────── Port (接口边界) ─────────────    │
├─────────────────────────────────────────────────┤
│  L3  领域层 (Domain)                             │
│      纯逻辑。卡片定义/标记/标签/效果/规则。         │
├─────────────────────────────────────────────────┤
│  L2  基础设施层 (Infrastructure)                  │
│      文件 IO、解析器、渲染引擎、素材加载。          │
├─────────────────────────────────────────────────┤
│  L1  素材层 (Assets)                             │
│      字体、图标、CSS Token。不包含代码。            │
├─────────────────────────────────────────────────┤
│  L0  运行时层 (Runtime)                           │
│      战场模块。实例化、区域管理、状态变更、          │
│      效果结算、对局存档。                          │
└─────────────────────────────────────────────────┘
```

### 3.2 依赖方向（单向，不可逆转）

```
L5 ──→ L4 ──→ Port (接口) ←── L2                         ←── L0
                              ↑                               ↑
                          L3 ──┘                               │
                          ↑                                 L1 ─┘
                      L1 ←─┘ (L3 通过 Port 间接引用 L1)
```

| 层 | 名称 | 依赖方向 |
|:--:|------|---------|
| L5 | 呈现层 | → L4 → Port |
| L4 | 应用层 | → Port → L0 |
| L3 | 领域层 | 零外部依赖 |
| L2 | 基础设施层 | 实现 Port |
| L1 | 素材层 | 被 L2 管理，不引用任何层 |
| L0 | **运行时层** | → L3（读取静态定义）+ L2（调用渲染/素材）+ L1（调用素材） |

## 第三章：接口契约体系

### 3.1 Port 设计总则

每个 Port 是一个 trait（Rust）或 interface（TypeScript），定义一组函数签名。Port 的命名规则：`{能力域}Port`。

### 3.2 核心 Port 清单

```
Port                  职责                            实现方（L2）
────────────────────  ──────────────────────────────  ──────────────────
CardRepositoryPort    卡的增删改查、遍历、导入导出        FileCardRepository
TagDictionaryPort     标签查询、合法性校验、别名解析       BundledTagDictionary
MarkRegistryPort      标记名注册、类型查询                BundledMarkRegistry
ParserPort            文本→AST，校验                     DZParser
DuelEnginePort        对战初始化、Step、状态查询           DuelEngine
BattlefieldPort       运行时实例化、区域管理、状态变更        BattlefieldModule
RenderPort            卡面渲染（源格式→PNG/SVG）          CanvasRenderer
AssetLoaderPort       按关键词加载素材文件                FsAssetLoader
ConfigPort            读写全局配置                        JsonConfigStore
LogPort               诊断日志、错题集                    DevToolsLogger
BatchOutputPort       批量产出卡面（配比表→PNG序列）        BatchRenderer
AIAssistantPort       语法生成/校验/补全 的 AI 辅助         OpenAIAssistant / LocalModelAssistant
```

### 3.3 Port 定义示例

```
// Rust trait 示例

pub trait CardRepositoryPort: Send + Sync {
    fn list_all(&self) -> Result<Vec<CardId>, RepoError>;
    fn load(&self, id: &CardId) -> Result<CardBundle, RepoError>;
    fn save(&self, bundle: &CardBundle) -> Result<(), RepoError>;
    fn delete(&self, id: &CardId) -> Result<(), RepoError>;
    fn exists(&self, id: &CardId) -> bool;
}

pub trait ParserPort: Send + Sync {
    fn parse(&self, source: &str) -> Result<CardAst, ParseError>;
    fn validate(&self, ast: &CardAst, tags: &dyn TagDictionaryPort) -> Vec<ValidationIssue>;
}
```

```
// TypeScript interface 示例

interface CardRepositoryPort {
  listAll(): Promise<Result<CardId[]>>;
  load(id: CardId): Promise<Result<CardBundle>>;
  save(bundle: CardBundle): Promise<Result<void>>;
  delete(id: CardId): Promise<Result<void>>;
}

interface RenderPort {
  renderCard(bundle: CardBundle): Promise<Result<Blob>>;
  renderPreview(ast: CardAst): Promise<Result<Blob>>;
}
```

### 3.4 模块注册与组装

初始化时由一个 `ModuleRegistry` 完成所有 Port 的绑定：

```
// 启动时的组装代码（唯一知道"谁实现谁"的地方）

registry.register<CardRepositoryPort>(FileCardRepository::new(cards_dir));
registry.register<TagDictionaryPort>(BundledTagDictionary::new());
registry.register<MarkRegistryPort>(BundledMarkRegistry::new());
registry.register<ParserPort>(DZParser::new());
registry.register<RenderPort>(CanvasRenderer::new());
registry.register<AssetLoaderPort>(FsAssetLoader::new(assets_dir));
registry.register<ConfigPort>(JsonConfigStore::new(config_path));
registry.register<LogPort>(DevToolsLogger::new(log_path));

// UseCase 从 registry 获取自己需要的 Port
let card_repo = registry.get::<CardRepositoryPort>();
let parser = registry.get::<ParserPort>();
```

组装代码是**唯一知道具体实现类的地方**。其他所有代码只看到 trait。

### 5.5 删除卡牌的影响范围

```
删除 cards/ZY01-儒家/ 目录 = 

  ① FileCardRepository 下次遍历时不再加载 ZY01
  ② 如果卡库中有其他卡引用了"儒家"（如兵家转职列表），

  ④ 零崩溃、零孤儿数据、零级联删除

这就是"删除文件夹 = 删除卡牌"的全部含义。
```

## 第六章：UI 即投影

### 6.1 投影映射表

UI 上的每个非固定元素，背后都必须有一个领域实体：

```
UI 元素                 领域实体/模块          数据来源
──────────────────────  ────────────────────  ──────────────
卡牌列表                CardRepositoryPort     cards/ 目录遍历
单卡详情面板            CardBundle             单个卡片目录
卡面预览图              RenderPort             渲染引擎产出
标签筛选下拉框          TagDictionaryPort      标签字典
标记提示 tooltip        MarkRegistryPort       标记注册表
效果描述文本            CardAst (来自 Parser)   card.dz 解析结果
语法错误提示            ParserPort.validate()  card.dz → AST 校验
素材图标                AssetLoaderPort        assets/ 目录
主题色彩值              ConfigPort + CSS Token CSS 变量文件
对战面板玩家状态        DuelEnginePort         对战引擎
```

### 6.2 投影规则

```
UI 组件 = f(DTO)

DTO = UseCase 从领域模块组装出的纯数据对象

UI 组件从不直接调用领域模块，只接收 DTO
DTO 变化 → React 重新渲染
```

### 6.3 例子：卡牌列表页的完整投影链

```
CardsPage (UI)
  ↓ 使用 useCards() hook
useCards (Application)
  ↓ 调用 CardRepositoryPort.listAll()
FileCardRepository (Infrastructure)
  ↓ 遍历 cards/ 目录，读取每个 card.dz
DZParser (Infrastructure, 通过 ParserPort 调用)
  ↓ 解析 card.dz → CardAst
  ↓ 校验 CardAst
  ↓ 组装 CardBundle { meta + ast + preview_path }
  ↓ 返回 Vec<CardBundle>
useCards 将 CardBundle 转为 CardDto
CardsPage 将 CardDto[] 渲染为 <CardList> + <CardItem>
```

任何一步出了问题，错误在对应模块内部处理，不向 UI 泄漏异常。

### 7.2 素材调用方式

```
// 共享素材：通过关键词调用
AssetLoaderPort::load("icon-category-阵营") → shared/icons/category-阵营.svg
AssetLoaderPort::load("bg-rarity-白")       → shared/bg/card-bg-白.png

// 卡牌专属素材：通过卡牌 ID + 素材名调用

// 3. 素材文件各自独立，没有交叉引用
```

### 7.3 素材缓存

```
AssetLoaderPort 内部维护 LRU 缓存：
- 已加载的素材缓存在内存
- 缓存上限可配置（默认 32MB）
- 卡牌被删除时，该卡专属素材从缓存清除
- shared 素材常驻缓存（全局共享，永不卸载）
```

## 第八章：运行时层 — 战场模块

战场模块（BattlefieldModule）是整个架构唯一的"写状态"模块。它位于 L0 层，在运行时负责将静态卡牌定义实例化、管理对局中的区域与状态流转。

### 8.1 战场模块的核心数据结构

```
// Rust 示例

struct Battlefield {
    players: Vec<Player>,
    zones: ZoneMap,                   // 所有区域
    turn: u32,                        // 当前回合数
    phase: Phase,                     // 当前阶段
    effect_stack: Vec<EffectEntry>,   // LIFO 效果栈
    log: Vec<LogEntry>,               // 操作日志
}

struct Player {
    id: PlayerId,
    faction: StaticCardId,            // 阵营：ZY01
    career: StaticCardId,             // 职业：ZY06
    equipped: Vec<RuntimeCardId>,     // 已装备的构筑卡实例
    hand: Vec<RuntimeCardId>,
    deck: Vec<RuntimeCardId>,
    graveyard: Vec<RuntimeCardId>,
}

struct RuntimeCardInstance {
    runtime_id: RuntimeCardId,        // 如 "JB01_3"
    static_def_ref: StaticCardId,     // 如 "JB01"
    hp: u32,
    armor: u32,
    energy: u32,
    marks: HashMap<MarkId, u32>,      // 标记名 → 层数
    zone: Zone,                       // 当前所在区域
    owner: PlayerId,
}
```

### 8.2 战场模块与静态仓库的关系

```
战场模块初始化时的数据流：

cards/ 目录（静态仓库）
  │
  ├─→ CardRepositoryPort.list_all()
  │     返回 78 个 StaticCardId
  │
  ├─→ 战场模块读取配比表
  │     JB01 击敌 ×12   → 生成 JB01_1 ~ JB01_12
  │     JB02 御守 ×6    → 生成 JB02_1 ~ JB02_6
  │     GZ04 长剑 ×2    → 生成 GZ04_1 ~ GZ04_2
  │     ...
  │     总计生成 157 个运行时实例
  │
  ├─→ 每个实例 { runtime_id, static_def_ref, 初始状态 }
  │     runtime_id 是唯一的，static_def_ref 全部指向 cards/ 下的同一份 card.json
  │
  └─→ 实例进入牌堆区 → 洗牌 → 对局开始
```

### 8.3 在 UI 中展示同一卡牌的不同实例

当对局中有 4 张「击敌」在手牌中时：

```
UI 层请求:
  useBattlefield() → BattlefieldPort.get_player_hand(player_id)

战场模块返回:
  [
    { runtime_id: "JB01_3",  static_def: "JB01", hp: 0, armor: 0, ... },
    { runtime_id: "JB01_7",  static_def: "JB01", hp: 0, armor: 0, ... },
    { runtime_id: "JB01_9",  static_def: "JB01", hp: 0, armor: 0, ... },
    { runtime_id: "JB01_11", static_def: "JB01", hp: 0, armor: 0, ... },
  ]

UI 渲染:
  4 张相同的卡面，但左上角标注运行时序号 _3、_7、_9、_11
  点击任意一张 → 以 runtime_id 为参数发送操作指令
```

### 8.4 BattlefieldPort 接口定义

```
pub trait BattlefieldPort: Send + Sync {
    // 初始化
    fn init_game(&mut self, player_count: u32) -> Result<(), BattlefieldError>;

    // 区域查询
    fn get_player_hand(&self, player: PlayerId) -> Vec<RuntimeCardInstance>;
    fn get_player_field(&self, player: PlayerId) -> Vec<RuntimeCardInstance>;
    fn get_player_deck_count(&self, player: PlayerId) -> u32;

    // 操作
    fn draw_card(&mut self, player: PlayerId) -> Result<RuntimeCardId, BattlefieldError>;
    fn play_card(&mut self, player: PlayerId, card: RuntimeCardId, target: Option<PlayerId>) -> Result<EffectResult, BattlefieldError>;
    fn discard_card(&mut self, player: PlayerId, card: RuntimeCardId) -> Result<(), BattlefieldError>;

    // 状态查询
    fn get_turn(&self) -> u32;
    fn get_phase(&self) -> Phase;
    fn get_effect_log(&self) -> Vec<LogEntry>;

    // 存档
    fn save_snapshot(&self, path: &Path) -> Result<(), BattlefieldError>;
    fn load_snapshot(&mut self, path: &Path) -> Result<(), BattlefieldError>;
}
```

### 8.5 战场模块不做什么

- ❌ 不渲染卡面图片（调用 RenderPort）
- ❌ 不加载素材文件（调用 AssetLoaderPort）
- ❌ 不解析效果文本（ParserPort 已经在初始化前完成解析）
- ❌ 不修改静态卡牌定义（只读 cards/ 目录）
- ❌ 不处理 UI 交互（只返回数据，UI 自行决定如何展示）

## 第九章：批量产出模块

批量产出模块专注于将静态卡牌定义"按配比展开为物理实体"并渲染为线下可印刷的卡面文件。

### 9.1 使用场景

```
设计师完成了一张「击敌」的设计 → 原始套配比表规定击敌需要 12 张
  → 批量产出模块自动生成 12 张卡面 PNG：
      JB01_1-击敌.png
      JB01_2-击敌.png
      ...
      JB01_12-击敌.png

全部 157 张实体卡一次性产出 → 157 个 PNG 文件 → 印刷厂直接制版
```

### 9.2 数据来源

批量产出模块读取两个数据源：

```
① 静态卡牌定义：cards/{id}/card.dz + meta.json   （78 种）
② 发行配比表：   cards/_distribution.json          （配比数据）

_distribution.json 结构：
{
  "set": "原始套",
  "version": "1.0.0",
  "cards": [
    { "id": "JB01", "name": "击敌", "count": 12 },
    { "id": "JB02", "name": "御守", "count": 6 },
    { "id": "GZ04", "name": "长剑", "count": 2 },
    ...
  ]
}
```

### 9.3 产出流程

```
BatchOutputPort.generate_set(set_name)
  │
  ├─→ ① 读取 _distribution.json
  │
  ├─→ ② 遍历每张卡：
  │     for each 配比条目：
  │       for i in 1..count：
  │         运行时 ID = "{id}_{i}"
  │
  ├─→ ③ 对每个运行时 ID：
  │     a. 从 cards/{id}/ 读取 card.dz → ParserPort.parse()
  │     b. CardBundle { meta, ast, runtime_id }
  │     c. RenderPort.render_card(bundle) → PNG blob
  │     d. 写入 output/{set_name}/{id}_{i}-{name}.png
  │
  └─→ ④ 产出 output/{set_name}/_manifest.json
        列出全部产出文件的 ID、名称、路径映射
```

### 9.4 产出目录结构

```
output/
  原始套/
    _manifest.json           ← 全部 157 张的索引
    JB01_1-击敌.png
    JB01_2-击敌.png
    ...
    JB01_12-击敌.png
    JB02_1-御守.png
    ...
    GZ04_1-长剑.png
    GZ04_2-长剑.png
    ...
    总计 157 个 PNG 文件
```

## 第十章：AI 辅助模块

AI 模块通过 API 接入外部大语言模型，帮助设计师加快创作流程。所有 AI 操作必须通过 AIAssistantPort 接口，实现方可随时替换（OpenAI / 本地模型 / 其他 API）。

### 10.1 核心能力

```
能力 A — 语法生成：
  设计师输入："武学，被动，受到伤害时免疫一次并抽牌"
  AI 返回：
    浮光 [武学, 被动]
      受到伤害时，消耗1张紫卡，将本卡效果视为「免疫本次伤害」。
      规避成功后，抽取1张基本牌。
  
  流程：自然语言 → AI → DZ 语法 → ParserPort.validate() → 合法则返回，非法则 AI 自修正

能力 B — 语法校验与修正：
  设计师输入了一段有错误的 DZ 语法
  AI 根据词条库和语法规范，指出错误并提供修正建议

能力 C — 补全建议：
  设计师写到一半："受到伤害时，"
  AI 根据上下文推荐合法的后续（谓语、宾语、备注）

能力 D — 配比建议：
  设计师设计了一张新卡牌
  AI 分析现有卡池的平衡性，推荐合理的发行数量
```

### 10.2 安全保障

AI 产出的所有内容必须经过 ParserPort 校验才允许写入 card.dz：

```
AIAssistantPort.generate(prompt)
  │
  ├─→ ① 调用 AI API → 原始 DZ 文本
  │
  ├─→ ② ParserPort.parse(dz_text)
  │     ├─→ 解析成功 → ③
  │     └─→ 解析失败 → 将错误信息作为上下文再次调用 AI → 回到 ①
  │         （最多重试 3 次，3 次仍失败则返回最佳尝试 + 错误列表）
  │
  ├─→ ③ ParserPort.validate(ast, tag_dict, mark_registry)
  │     ├─→ 全部通过 → 返回 CardAst
  │     └─→ 有 warnings → 返回 CardAst + warnings 列表（用户自行判断）
  │
  └─→ ④ 系统**绝不**直接将 AI 产出写入 cards/ 目录
        必须由设计师手动确认后才写入
```

### 10.3 AIAssistantPort 接口

```
pub trait AIAssistantPort: Send + Sync {
    fn generate_card(
        &self, 
        prompt: &str,                     // 设计师的自然语言描述
        context: &AIContext,              // 词条库、现有卡池、语法规范
    ) -> Result<AIGeneratedCard, AIError>;

    fn validate_and_fix(
        &self,
        dz_text: &str,
        errors: &[ParseError],
    ) -> Result<String, AIError>;         // 返回修正后的 DZ 文本

    fn suggest_completion(
        &self,
        partial_dz: &str,                 // 写到一半的 DZ 文本
        cursor_position: usize,
    ) -> Result<Vec<CompletionSuggestion>, AIError>;
}

struct AIContext {
    lexicon: String,                      // 词条库的完整内容
    existing_cards: Vec<CardSummary>,     // 现有卡池摘要（名称+类型+标签）
    grammar_spec: String,                 // DZ 语法规范全文
    distribution_rules: String,           // 发行配比规则
}
```

## 第十一章：对战系统

对战系统是整个项目的"消费端"——编辑器和批量产出负责"生产卡牌"，对战系统负责"消耗卡牌"。它基于战场模块（L0）构建，向上提供完整的对局体验。

### 11.1 对战系统的分层位置

对局过程中各层如何协作（以"玩家 A 打出击敌攻击玩家 B"为例）：

```
UI 层 (L5): 玩家点击击敌卡 → 选择目标 B → 调用 useDuel().playCard("JB01_3", target=B)
  │
应用层 (L4): PlayCardUseCase → BattlefieldPort.play_card(A, "JB01_3", B)
  │
运行时层 (L0): BattlefieldModule
  │  ① 验证：JB01_3 在 A 的手牌中？B 是合法目标？
  │  ② 执行支付：A 消耗 1 次攻击次数
  │  ③ 加载静态定义：CardRepositoryPort.load("JB01") → meta + ast
  │  ④ 执行效果：读取 CardAst → 逐条结算 → 更新 B 的 HP
  │  ⑤ 记录日志：LogEntry { action: "play_card", actor: "JB01_3", target: "B", result: "1 点物理伤害" }
  │
  ↓ 返回 EffectResult { success: true, log: [...], state_changes: [...] }
  │
资产层 (L1): UI 在结算过程中调用 AssetLoaderPort 加载击敌的卡面图片用于动画
基础设施层 (L2): RenderPort 渲染伤害数字特效
```

### 11.2 对战系统的核心数据流

```
对局初始化 (init_game)
  │
  ├─→ 读取配比表 _distribution.json
  ├─→ CardRepositoryPort.load_all() → 78 个静态定义
  ├─→ 生成 157 个运行时实例 RuntimeCardInstance
  ├─→ 按玩家数分区洗牌、分配阵营/职业/初始装备
  └─→ 各玩家从牌堆抽初始手牌
       │
       ▼
    回合循环 (next_turn)
       │
       ├─→ 触发回合开始时效果（儒家·仁心、道家·道法 等）
       ├─→ 玩家行动阶段（play_card / equip / skill）
       │     │
       │     ├─→ ParserPort 未参与（效果已在 init 时解析为 AST）
       │     ├─→ BattlefieldModule 按 AST 逐条执行支付→结算→连锁
       │     └─→ 所有状态变更通过 effect_stack（LIFO）管理
       │
       ├─→ 触发回合结束时效果（止波、法家·法令 等）
       └─→ 检查胜负条件 → 继续/结束
```

### 11.3 三端适配

```
线下端（实体卡）：
  对战系统提供「打印用回合记录表」和「手动结算指南」
  → 批量产出模块生成实体卡 + DuelEnginePort 输出纯文本结算步骤

PC 端（桌面）：
  完整交互界面：鼠标拖拽出牌、点击目标、动画效果、日志面板
  → Tauri 原生窗口 + React 渲染

移动端（横屏）：
  PC 端 UI 的响应式变体，触摸优化
  → 相同 React 代码 + 媒体查询 + 横屏锁定
  → 手牌区在底部、对手在上方、中间为对战区域

三端共享同一份 Rust 后端逻辑（DuelEnginePort + BattlefieldPort）
三端仅 UI 层不同
```

### 11.4 对战模块的 Port 分工

```
DuelEnginePort  — 对战抽象规则（init/step/phase/turn/win_condition）
BattlefieldPort — 实例化管理（手牌区/场上/坟场/HP/护甲/标记）
                  这是唯一写状态的 Port
ParserPort      — 效果结算时读取 AST（不重新解析）
RenderPort      — 伤害数字、卡面动画等视觉特效
AssetLoaderPort — 卡面图片、音效
```

### 11.5 对局存档

```
对局中途存档：
  BattlefieldPort.save_snapshot(path)
    → 将整个 Battlefield 序列化为 JSON
    → 包含所有 RuntimeCardInstance 的完整状态
    → 文件大小约 50-200KB（157 张实例）

对局回放：
  BattlefieldPort.load_snapshot(path)
    → 恢复完整战场状态
    → 配合 effect_log 逐条回放操作

对局结束：
  保留最终状态快照 + 完整 effect_log
  可用于赛后复盘分析
```

## 第十三章：与历史经验教训的对照

| # | 历史教训 | 0.10.0 架构如何应对 |
|---|---------|-------------------|
| 1 | 模板引擎无法替代语言 | card.dz 使用完整 DZ 语言，不再用模板拼参数 |
| 2 | 编辑器必须直接操作语法 | 编辑器打开的就是 card.dz，所见即所存 |
| 3 | 分类必须体现领域划分 | cards/ 目录的物理结构就是五大类的映射 + tags/ 独立目录 |
| 4 | Crate 必须有交叉依赖 | 通过 Port trait 产生"逻辑依赖"，而非 compile-time 依赖。tag crate 的 trait 被 parser 消费 |
| 5 | 支付与效果严格区分 | 解析器内建三段式执行顺序模型 |
| 6 | 两套数据命名映射 | 所有数据统一在 cards/ 目录下，命名采用官方名称，无脱敏版 |
| 7 | 声明行冗余 | meta.json 存储属性，card.dz 存储效果。职责分离 |
| 8 | 数据加载空文件保护 | FileCardRepository 独立处理降级：空→种子数据→空卡池优雅 |
| 9 | 五段式语法不宜直接编辑 | card.dz 是自然中文，card.json 是编译后的 AST |
| 10 | `？` 与 `若` 区分 | 解析器规则内置，编辑器补全提示 |
| 11 | 主语省略 | DZ 语法天然支持 |
| 12 | 语法靠近人类语言 | DZ 语法句号结尾，标记仅 `：` `？` `·` `—` `[ ]` `「」` |

## 第十五章：打开文件的物理路径

这是一个有价值的设计细节。当用户在编辑器中打开"浮光"，程序的路径解析链：

```
用户在 UI 点击"浮光"
  → CardView 收到 CardDto { id: "GZ21", name: "浮光" }
  → EditCardUseCase.load("GZ21")
  → CardRepositoryPort.load("GZ21")
  → FileCardRepository 拼接路径：
       cards_dir + "/GZ21-浮光/card.dz"      ← 编辑的目标文件
       cards_dir + "/GZ21-浮光/card.json"    ← 上一次编译结果（对比用）
       cards_dir + "/GZ21-浮光/meta.json"    ← 元数据
  → 返回 CardBundle { source, ast, meta }
  → UI 渲染编辑器 + 预览
```
