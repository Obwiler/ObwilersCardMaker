# 0.10.0 重构性更迭 — 前版本经验教训总结

> 本文档基于 0.8.3 → 0.8.4 → 0.8.5 → 0.9.0 → 0.9.1 → 1.0.0 六个版本的全部开发经验，
> 提炼出 12 条核心教训与 8 条红线注意事项，为 0.10.0 重构提供决策依据。

---

## 一、版本演进回顾

### 0.8.3 — 探路期
- 首个可运行版本骨架：Tauri v2 + React + TypeScript
- 四步编辑流程（选类型→填信息→配技能→预览导出）
- 建立了 `atomic/` `templates/` `store/` 的分层目录
- **关键经验**：卡牌类型分类在此时确定（阵营/职业/构筑/基本），后续未变

### 0.8.4 — 原子化膨胀期
- 引入「目标选择系统」：24 种目标类型 + 12 个过滤器 + 5 个排序器
- 21 个效果模板（6 条件 + 6 消耗 + 9 效果）
- `SELF_CHECK_BENCHMARK.md` 自检基准
- `PROJECT_PLAN.md` 统合规划书（文档规模膨胀到 2000 行）
- **关键经验**：模板数量开始失控，但问题尚未暴露

### 0.8.5 — 渲染增强期
- 新增卡面预览和 PNG 导出功能
- 设置页面（Settings.tsx）
- HTML 静态渲染验证（render.html）
- **关键经验**：前端看似功能齐全，但尚未接入真实的卡牌数据

### 0.9.0 — 语法觉醒期
- 五段式语法规范成形（条件→主→谓→宾→备注）
- 新增 `fiveSegment.ts` 五段式模板
- `grammar-rules.json` 语法规则配置数据
- `grammarValidator.ts` 语法校验器
- 157 张卡牌的完整语法条目在 CardRules 文件夹中完成
- **关键经验**：五段式语法是重大突破，但表格形式的编辑体验极差

### 0.9.1 — 审计修复期
- 共修复 12 个前端 Bug（#8-#19）
- 尝试 Android APK 构建（因环境缺 SDK 失败）
- 数据加载 Bug 导致"卡牌总数为 0"——根因是 AppData 中存在空 cards.json
- **关键经验**：数据加载的鲁棒性比想象的更重要

### 1.0.0 — 架构反思期
- 审计报告揭示核心问题：
  - Rust 端 5 个 crate 零交叉引用，所有集成压在 lib.rs 胶水层（31 个命令）
  - core crate 未被任何其他 crate 依赖——共享基础类型完全浪费
  - parser（1704 行）和 duel（2398 行）完全零测试
  - 三套独立的 Card 类型定义（core::Card, parser::Card, duel::Card）互不兼容
- 重构计划书提出 DDD + 六边形架构
- **关键经验**：扁平架构（零依赖）不等于好架构。模块间必须有有意义的交叉。

## 二、12 条核心教训

### 教训 1：模板引擎无法替代语言

0.8.x 时代的核心思路是"用 21 个模板拼出所有卡牌效果"。这在简单卡牌（击敌、御守）上可行，但面对浮光的嵌套免疫、药师的配方系统、兵家的双职业机制时完全崩溃。

**根因**：模板是**闭合系统**，卡牌效果是**开放系统**。21 个模板 × N 个参数的排列组合永远无法覆盖 40+ 个谓语动词 × 14 种主语 × 无限的嵌套层数。

**0.10.0 方案**：放弃模板引擎，采用 DZ 领域特定语言。用户书写自然中文效果描述，解析器解析为 AST。语言本身就是界面。

### 教训 2：编辑器 UI 必须直接操作语法，而非间接映射

0.9.x 时代的问题是"Rust 端有完整的五段式解析器，前端还在用下拉框拼参数"。这两层之间存在手动翻译代码（lib.rs 胶水层），任何新增卡牌类型都需要同步修改两端。

**0.10.0 方案**：编辑器直接操作 DZ 源格式文本。输入即解析，解析即预览。不经过中间格式。

### 教训 3：上层分类必须体现领域划分

0.8.x 时代把"标记"当作卡牌效果的附属物，散落在各张卡牌描述中。实际上标记（仁心、自然、噬魂等 9 种）有独立的生命周期（产生→积累→消耗→移除），是独立于卡牌的领域实体。不给标记独立管理入口，就无法安全地引入"新卡牌引用已有标记"。

**0.10.0 方案**：五大类体系明确包含「标记类」。标记是纯资源定义，不绑定任何卡牌的效果描述。

### 教训 4：Crate 必须有意义的交叉依赖

1.0.0 审计发现：5 个 Rust crate 互不依赖，tag 不知道 parser 需要什么，parser 不向 duel 提供输出格式。所有集成压在 lib.rs 一个文件里做手工转换。

**0.10.0 方案**：Domain 层统一定义共享类型（Card, Tag, Rule, Effect）。parser 消费 tag（标签合法性校验），duel 消费 parser（CardAst → DuelCardInit）。每个 crate 既消费也产出。

### 教训 5：支付与效果必须严格区分

对话中暴露的最大概念漏洞：纯洁的"清空技力护甲"是效果行为（濒死自毁），不是支付。除障的"移除护甲"是对自己使用的效果，也不是支付。混淆这两者会导致结算逻辑完全错误。

**0.10.0 方案**：语法规范第三章明确定义「支付阶段→效果结算阶段→后续连锁阶段」的三段式执行顺序，区分消耗（支付）vs 扣除/移除（效果），统一数值引用的时点规则。

### 教训 6：两套数据集的命名映射必须显式维护

CardRules 文件夹（完整版：儒家/道家/法家/墨家/兵家）和 对峙/ 文件夹（皮套脱敏版：智械/王灵/兽族/人族/无形）之间的映射关系从未在任何文档中正式记录。这导致 AI 和开发者在使用数据时频繁混淆。

**0.10.0 方案**：在辞典中明确标注所有卡牌的正式名称。皮套脱敏版仅作为参考对照，不做数据源。

### 教训 7：声明行只保留类型必要信息

历史版本中声明行堆砌了大量冗余参数：`[武学, 被动, 上限2, 互斥:轻浮]`。上限 2 是所有构筑卡的通用规则（同名卡带 2 张），互斥是约束备注应归入效果行，不应混在类型声明中。

**0.10.0 方案**：声明行极简化。阵营卡写面板属性（必要），构筑卡写子类型和主动/被动（必要）。其余全部省略或归入备注。

### 教训 8：数据加载必须有空文件保护

0.9.1 的 0 卡牌 Bug 源于 `init_cards()` 中只有 `!path.exists()` 才触发播种，但 AppData 存在一个空的 `cards.json` 导致播种被跳过。

**0.10.0 方案**：加载前校验文件内容长度。 `< 10 字节` → 回退到种子数据。三级降级：cards.json → cards.json.bak → backups/ → 种子数据 → 空卡池优雅降级。

### 教训 9：五段式语法强大但不宜直接编辑

五段式表格（条件→主→谓→宾→备注）的完备性毋庸置疑（157 张全部可描述），但它在编辑器中需要逐格填写，人工操作的认知负荷极高。

**0.10.0 方案**：表格用于底层存储（AST），源格式用于上层编辑。用户写的是自然中文，解析器转化为五段式 AST。

### 教训 10：条件分支的 `？` 必须严格区分互斥与非互斥

早期 DZ 语法中 `？` 被滥用于"若目标有护甲"这种顺序触发的独立条件。`？` 仅应用于翻牌判定等真正的互斥分支（A 和 B 不能同时发生）。

**0.10.0 方案**：`？` 仅用于互斥判定分支，`若` 用于顺序触发的独立条件检查。

### 教训 11：主语省略是正确设计

五段式语法中"自身"作为主语出现率 > 90%。DZ 语法默认主语 = 自身，仅在切换时显式写出，消除了大量冗余。

**0.10.0 方案**：保持这一设计。仅「对目标」「攻击者」「对伤害来源」「该紫卡效果」等少数情况下写出主语。

### 教训 12：语法必须靠近人类语言

0.10.0 初期版本的 DZ 语法使用了 `→` `:` `·` `|` 等编程符号，读起来像代码而非游戏规则书。用户反馈正确：卡牌设计者需要的是读起来像规则说明书的语法。

**0.10.0 方案**：符号仅作为解析锚点保留最小集（`：` `—` `？` `·` `[ ]` `「」`），语句本身是完全的自然中文，句号结尾。

## 三、8 条红线注意事项

| # | 红线 | 已违反的版本 | 后果 |
|---|------|:--:|------|
| 1 | **禁止模板推演代替语言设计**——不要用有限模板覆盖无限规则 | 0.8.x | 复杂卡牌无法准确表达 |
| 2 | **禁止前端后端各自定义一套类型**——只能有一套共享类型 | 1.0.0 | 三套 Card 类型互不兼容 |
| 3 | **禁止标记绑定卡牌效果**——标记是纯资源，效应由卡牌描述 | 0.10.0 初版 | 新卡无法引用标记 |
| 4 | **禁止胶水层承载业务逻辑**——lib.rs 只能是薄路由 | 1.0.0 | 31 个命令全部手动转换 |
| 5 | **禁止备注栏写条件判断和分支结果**——备注仅四类 | 多个版本 | 解析器无法识别隐藏逻辑 |
| 6 | **禁止宾语栏含动词**——谓语和宾语严格分离 | 多个版本 | 解析歧义 |
| 7 | **禁止同一行内隐式切换主语**——主语变就换行 | 多个版本 | 结算顺序混乱 |
| 8 | **禁止声明行堆砌通用规则**——上限 2、数量 N 是通用规则，不写 | 0.10.0 初版 | 每张卡重复冗余信息 |

## 四、0.10.0 技术路线决策

| 决策 | 选择 | 否决方案 | 理由 |
|------|------|---------|------|
| 编辑范式 | 语法文本编辑器（类 IDE） | 模板下拉框编辑器 | 语言表达力远超模板组合 |
| 存储格式 | DZ 源格式（自然中文） | 五段式表格 | 人类可读写，IDE 友好 |
| 解析层 | Rust parser（已有 lexer+parser+validator） | 全新解析器 | 已有 ~1700 行解析器可用 |
| 前端框架 | React 18 + TypeScript | 不换 | 已有完整组件树 |
| 后端架构 | Domain 层统一类型 + Application 层用例 | 扁平 crate 隔离 | 消除类型重复和胶水层膨胀 |
| 语法风格 | 自然中文语句，句号结尾 | 记号前缀风格（> + @ #） | 读起来像游戏规则 |
| 标记管理 | 独立标记类，纯资源定义 | 作为卡牌附属物 | 新卡可自由引用已有标记 |
| 支付原则 | 规范第二章明确定义三段式执行顺序 | 隐式规则 | 避免结算歧义 |

## 五、0.10.0 最小可用版本目标

第一阶段（编辑器核心）：
- 语法高亮文本编辑器 + 词条自动补全
- Rust parser 实时解析 → 校验结果即时反馈
- 卡面预览实时渲染
- 五大类卡牌类型完整支持

第二阶段（辞典与数据）：
- 原始套 78 种卡牌全部内置为预设
- 标记独立管理面板
- JSON 导出/导入

第三阶段（对战引擎）：
- 基于 DZ 语法的对抗模拟
- 效果结算日志可视化
- 15 标签联动体系落地
