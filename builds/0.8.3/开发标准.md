# CardMaker 开发标准

## 一、通用准则

### 1.1 语言规范

- 所有源码注释、变量名、函数名、提交信息统一使用**英文**。
- 所有面向用户的文本（UI 文案、提示信息、错误消息）、文档、思考过程统一使用**中文**。
- 枚举值的 key 使用英文（方便程序匹配），但 UI 展示必须通过中文标签映射转换。

### 1.2 代码风格

- TypeScript 严格模式（`strict: true`）。
- 使用 `const` 和 `let`，禁止 `var`。
- 文件名：小写 + 连字符（kebab-case），如 `effect-deal-damage.ts`。
- 组件文件：PascalCase，如 `CardPreview.tsx`。
- 接口名以 `I` 开头，枚举名以 PascalCase 命名。
- 导出统一通过各目录的 `index.ts` 进行。

### 1.3 原子化解耦原则

- 每个效果/条件/消耗模板是**独立文件**，除类型定义外不依赖任何业务模块。
- 模板注册通过 `templates/index.ts` 的注册表模式统一管理。
- 新增模板时**禁止修改已有文件**（注册表除外），保证增量开发安全性。
- 公共类型定义统一放在 `src/atomic/` 目录。

## 二、版本管理规范

### 2.1 版本号规则

采用语义版本号（Semantic Versioning）：`主版本.次版本.修订版本`

| 变更类型 | 版本号变更 | 示例 |
|---|---|---|
| 破坏性 API 变更 | 主版本 +1 | 1.0.0 → 2.0.0 |
| 新增功能（向后兼容） | 次版本 +1 | 0.8.2 → 0.8.3 |
| Bug 修复 | 修订版本 +1 | 0.8.2 → 0.8.3（如果只是修复） |

实际版本号记录在三个文件中，必须保持一致：
- `package.json` 的 `version` 字段
- `src-tauri/Cargo.toml` 的 `[package] version` 字段
- `src-tauri/tauri.conf.json` 的 `version` 字段

### 2.2 版本归档

每当完成一个新版本开发，在 `F:\TOOLS\ObwilerCardMaker\` 下创建版本号命名的文件夹：

```
F:\TOOLS\ObwilerCardMaker\
├── 0.8.3\          ← 当前版本
├── 0.9.0\          ← 下一版本
└── ...
```

每个版本文件夹必须包含：
1. 完整源代码（不含 `node_modules` 和 `target`）
2. 构建产物（`release/` 目录下的 .exe 和 .msi）
3. 文档（`docs/` 目录）
4. 更新日志（`docs/更新日志.md`）

### 2.3 构建流程

每次修改代码后，必须执行完整的构建、打包、版本标记流程：

1. 更新三个文件中的版本号
2. 执行 `npm run tauri build`
3. 将最新 .exe 复制到桌面快捷方式指向的路径
4. 更新桌面快捷方式（目标路径：`E:\ZhuoMian`）
5. `git add` → `git commit` → `git tag v{版本号}` → `git push`
6. 复制完整项目到 `F:\TOOLS\ObwilerCardMaker\{版本号}\`

### 2.4 Git 规范

- 远程仓库：`Obwiler/supreme-goggles`（GitHub）
- 推送方式：SSH（因本机 HTTPS 443 端口被墙）
- SSH 密钥：`~/.ssh/id_ed25519_cardmaker`（密钥名"马维思"）
- Commit 信息格式：`类型: 简短描述`
  - `feat: 新增淘汰效果 EXECUTE`
  - `fix: 修复技能配置未持久化`
  - `refactor: 重写 exporters 自然语言生成`
  - `chore: 更新依赖版本`

## 三、新增功能开发流程

### 3.1 新增效果模板

1. 在 `EffectType` 枚举中添加新值（`src/atomic/enums.ts`）
2. 在 `src/templates/effects/` 下创建 `effect-{名称}.ts`，导出 `IAtomicEffect` 对象
3. 在 `src/templates/index.ts` 中导入并注册到 `effectTemplates`
4. 在 `src/utils/exporters.ts` 的 `generateCardDescription` 中添加对应的自然语言生成逻辑

### 3.2 新增条件模板

同上述流程，对应修改 `ConditionType`、`src/templates/conditions/`、注册表、导出器。

### 3.3 新增消耗模板

同上述流程，对应修改 `CostType`、`src/templates/costs/`、注册表。

### 3.4 新增过滤器/排序器

在 `FilterId` / `SorterId` 枚举中添加新值，在对应目录下创建新模块文件，并在 `src/target/` 注册。

### 3.5 校验机制

新增模板后，必须同步为 `src/utils/validators.ts` 添加对应的校验规则，确保导出 JSON 的数据完整性。

## 四、开发环境配置

### 4.1 路径约定

| 用途 | 路径 |
|---|---|
| 项目根目录 | `E:\CardMaker\` |
| Rust 工具链 | `E:\rustup\` |
| Rust 环境变量 | `RUSTUP_HOME=E:\rustup\.rustup` |
| Cargo 缓存 | `CARGO_HOME=E:\rustup\.cargo` |
| 桌面路径 | `E:\ZhuoMian\` |
| 版本归档 | `F:\TOOLS\ObwilerCardMaker\` |

### 4.2 可用命令

| 命令 | 用途 |
|---|---|
| `npm run dev` | 启动 Vite 开发服务器 |
| `npm run build` | TypeScript 编译 + Vite 构建 |
| `npm run type-check` | 仅 TypeScript 类型检查 |
| `npm run lint` | ESLint 代码检查 |
| `npm run format:write` | Prettier 代码格式化 |
| `npm run test` | Vitest 单元测试 |
| `npm run tauri dev` | Tauri 开发模式 |
| `npm run tauri build` | Tauri 生产构建 |

## 五、代码审查清单

在提交代码前，确认以下各项：

- [ ] 所有新增文本使用中文
- [ ] 枚举值使用英文 key，UI 展示使用中文标签映射
- [ ] 新增模板文件已在 `index.ts` 注册
- [ ] `exporters.ts` 已添加对应的自然语言生成逻辑
- [ ] `validators.ts` 已添加校验规则
- [ ] 三个版本号文件保持一致
- [ ] TypeScript 编译无错误（`npm run type-check`）
- [ ] 未引入新的 `any` 类型（除明确必要的场景）
- [ ] 未遗留 `console.log` 调试语句
