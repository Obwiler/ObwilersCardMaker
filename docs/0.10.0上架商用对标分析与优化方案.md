# 0.10.0 上架商用 — 对标分析 & 优化方案

> 基于 GitHub 主流卡牌编辑器/DLS/对战平台的开源项目调研，
> 结合 ObwilerCardMaker 当前架构现状，输出可执行的优化路线。
>
> 调研对象：Cockatrice、Forge、MSE、YGOPro/EDOPro、jinteki.net、Card Conjurer
> 项目现况：78 种卡牌、DZ 语法、七层架构、Rust parser + React 呈现、157 张实体

---

## 二、P0 优先级 — 必须在上架前完成

### 2.1 parser/duel 测试体系

**现状**：parser（1704 行）和 duel（2398 行）完全零测试，占后端总代码 85%。

**目标**：
- parser 测试覆盖 ≥ 60%（核心：78 张原始套卡牌的批量解析回归）
- duel 测试覆盖 ≥ 70%（核心：状态机所有合法/非法转换路径）

**具体方案**：

```
tests/
  parser/
    78_cards_parse.rs      ← 78 张原始套全部可解析，零 panic
    edge_cases.rs          ← 空文本、超长名称、未闭合括号、非法标记名
    tags.rs                ← 15 个标签定义的引用有效性
  duel/
    state_machine.rs       ← 5 阶段 → 3 回合完整流程
    effect_stack.rs        ← LIFO 栈结算顺序
    target_resolve.rs      ← 7 种目标类型的解析
    scenario.rs            ← 4 个预设场景初始化 + Step
    78_cards_effect.rs     ← 每张卡效果描述 → 效果对象映射正确
```

**验收标准**：`cargo test --workspace` 全部通过，至少 250+ 个测试用例。

---

### 2.2 所见即所得的卡牌编辑器

**现状**：编辑器页面框架存在，但未实现语法辅助编辑。

**目标**：实现完整的 DZ 语法编辑器。

**具体方案**：分三个子阶段

```
阶段 A — 语法高亮 + 实时解析（2-3 天）
  输入 card.dz 文本 → 300ms 防抖后 Rust parser 解析
  → 错误行红色波浪线 + 警告行黄色波浪线
  → 右侧实时预览卡面

阶段 B — 词条自动补全（1-2 天）
  光标位置 → parser 上下文感知 → 推荐合法词条
  触发时机：
    · 空行 → 触发条件词库或谓语动词
    · 输入「→ 标记名列表
    · 输入 [ → 备注约束列表
    · 输入动词后空格 → 宾语类型推荐

阶段 C — 标签浏览器 + 快速插入（1 天）
  侧边栏显示 15 个标签索引
  点击标签 → 插入完整的标签引用块到光标位置
```

### 2.3 数据鲁棒性加固

**现状**：审计发现 cards.json 空文件导致 0 卡牌 Bug。

**目标**：三级降级链 + 启动自愈。

**具体方案**：

```
启动加载数据的三级回退：
  ① 读取 cards/ 目录 → 解析所有 card.dz
  ② 如果①失败 → 读取 cards.json.bak
  ③ 如果②失败 → 读取 backups/ 最近备份
  ④ 如果③失败 → 从编译期嵌入的种子数据恢复
  ⑤ 如果④失败 → 空卡池（警告用户，但不崩溃）

每次成功加载后自动备份：
  · 备份目录：data/backups/
  · 保留最近 20 份
  · 备份文件命名：cards_{timestamp}.json
```

## 三、P1 优先级 — 显著提升商业品质

### 3.1 卡面分层渲染引擎

**现状**：卡面通过 CSS 变量 + HTML 渲染为 Canvas。功能可用但不支持模板化。

**目标**：参考 Card Conjurer 的分层渲染架构。

```
渲染管线：

Layer 1: 背景层 (bg)
  → 根据品质（白/蓝/紫/橙）选择底色 + 纹理

Layer 2: 边框层 (border)
  → 根据类型（阵营/职业/构筑/基本）选择边框样式
  → 品质颜色边框

Layer 3: 名称层 (title)
  → 卡牌名称居中/靠上
  → 使用 card-title.woff2 字体

Layer 4: 属性层 (stats)
  → 阵营卡显示 生命/护甲/技力 面板
  → 构筑卡显示子类型标签

Layer 5: 文本框层 (text)
  → 效果描述文本，自动换行
  → 标记名「」高亮渲染
  → 约束 [ ] 灰色渲染

Layer 6: 插图/图标层 (art)
  → 卡牌专属插槽
  → 职业/阵营图标

Layer 7: 叠加效果层 (fx)
  → 闪卡效果、边框发光（可选）
```

每层独立渲染后合成最终卡面。层与层之间无依赖，可以独立替换。

**输出格式**：PNG（360×500, 1080×1500 可配置缩放倍率）

### 3.2 卡面渲染模板系统

**目标**：让用户自定义卡面布局，不修改代码。

```
templates/
  对峙-默认/
    layout.json      ← 7 层布局描述
    theme.css        ← 颜色/字体变量
    card-bg-白.png
    card-bg-蓝.png
    card-bg-紫.png
    card-bg-橙.png

layout.json 结构：
{
  "name": "对峙·默认",
  "dimensions": { "width": 360, "height": 500 },
  "layers": [
    { "id": "bg",      "position": "full",        "source": "tokens.bg.{rarity}" },
    { "id": "border",  "position": "full",        "source": "tokens.border.{type}" },
    { "id": "title",   "position": { "x": 20, "y": 20 }, "font": "card-title" },
    ...
  ]
}
```

模板类似于 MSE 的 `.mse-style`，但对峙默认模板是项目预设，用户可以通过 JSON 创建新模板。

### 3.3 高级语法扩展（双层引擎）

**现状**：DZ 语法 + 15 标签可覆盖所有 157 张卡牌。

**目标**：为未来复杂性预留扩展通道，但不破坏现有语法。

```
架构：双层规则引擎

  Layer 1: DZ 语法解析（主引擎，覆盖 90%+ 的卡牌效果）
    文本 → 词法分析 → 五段式 AST → 效果对象

  Layer 2: Rhai 脚本层（扩展引擎，仅在 DZ 无法表达时启用）
    卡牌定义中可嵌入 Rhai 脚本块
    脚本仅用于"超出 DZ 表达能力"的复杂条件

  card.dz 中的 Rhai 块（可选，绝大多数卡不需要）：
    core_skill {
      仁怀
      获得白或紫基本牌时，积累1个「仁心」标记[每回合最多3个]。
      ${{
        // Rhai 脚本：当仁心数量与手牌数量有复杂交互时
        if ctx.marks["仁心"] > ctx.hand_size {
          ctx.trigger("仁心溢出", ctx.marks["仁心"] - ctx.hand_size);
        }
      }}
    }
```

**关键原则**：不强制使用 Rhai。157 张原始套全部只用 DZ 语法。Rhai 仅为未来预留。

### 3.4 插件化的 Port 实现替换

**现状**：Port trait 定义了接口，但初始化时硬编码了实现类的选择。

**目标**：通过配置文件决定使用哪个实现。

```json
// config/ports.json
{
  "CardRepositoryPort": "FileCardRepository",
  "ParserPort": "DZParser",
  "RenderPort": "CanvasRenderer",
  "AssetLoaderPort": "FsAssetLoader",
  "BattlefieldPort": "BattlefieldModule",
  "LogPort": "DevToolsLogger"
}
```

替换实现 = 改一行配置 + 重启。例如切换到 WebGL 渲染器：

```json
{ "RenderPort": "WebGLRenderer" }
```

## 四、P2 优先级 — 上架后的迭代方向

### 4.1 自包含包格式 `.ocm-set`

```
my-faction-set.ocm-set  ← 本质是一个 .zip 文件

解包后：
  _meta.json          ← 包名、作者、版本、创建日期
  cards/
    ZY01-儒家/
      card.dz
      meta.json
      preview.png
    ...
  templates/
    对峙·暗黑版/
      layout.json
      ...
  assets/
    custom-art/
      ...
```

用户 A 点击"导出卡包" → 生成 `.ocm-set` → 发给用户 B → 用户 B 点击"导入卡包" → 卡牌自动加入 `cards/` 目录。

### 4.2 基础国际化 (i18n)

**目标**：卡牌元数据支持多语言。不是翻译效果文本（那个由设计师负责），而是 UI 界面文字和类型标签的多语言。

```
locales/
  zh-CN.json    ← 简体中文（默认）
  en.json       ← 英文
  ja.json       ← 日文
```

i18n key 示例：
```json
{
  "ui.page.cards": "卡牌管理",
  "ui.page.duel": "对战",
  "type.camp": "阵营",
  "rarity.white": "白",
  "rarity.orange": "橙"
}
```

### 4.3 对战引擎 — 网络层预留

**现状**：duel crate 是本地状态机，通过 Tauri command 响应前端。

**目标**：架构已兼容未来多人网络对战。在当前架构中预留 WebSocket 切入点：

```
未来多人对战扩展：
  BattlefieldPort 的当前实现 = 本地 BattlefieldModule
  未来实现 = RemoteBattlefieldClient（WebSocket 连接远程服务器）
  
  RemoteBattlefieldClient：
    实现 BattlefieldPort trait
    内部通过 WebSocket 发送操作指令到服务器
    接收服务器状态更新 → 推送到前端

  前端代码零改动（只依赖 BattlefieldPort 接口）
```

### 4.4 软件更新机制

Tauri v2 内置自动更新支持：

```
tauri.conf.json:
  "updater": {
    "active": true,
    "endpoints": ["https://cardmaker.example.com/updates/{{target}}/{{current_version}}"],
    "pubkey": "YOUR_PUBLIC_KEY"
  }
```

配合 GitHub Releases 发布版本，用户启动时自动检测更新。
