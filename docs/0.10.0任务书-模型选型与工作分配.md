# 0.10.0 任务书 — 模型选型与工作分配

> 目标：基于 DeepSeek4 Pro 和 DeepSeek4 Flash 两款模型的能力特征，
> 将 0.10.0 重构任务拆解为 7 个阶段 42 项任务，每项任务标注推荐模型和理由。

---

## 一、模型选型分析

### 1.1 两款模型的本质差异

| 维度 | DeepSeek4 Pro | DeepSeek4 Flash |
|------|:--:|:--:|
| **核心优势** | 复杂推理、长链规划、代码正确性 | 速度极快、成本极低、大规模产出 |
| **类比** | 架构师 + 高级工程师 | 熟练的编码助手 + 测试生成器 |
| **最适合** | 架构设计、Rust 核心引擎、状态机 | React 组件、JSON 数据、测试用例、文档 |
| **不适合** | 批量重复劳动（浪费推理能力） | 需要上下文推断的复杂 bug 修复 |
| **典型任务时长** | 2-10 分钟 / 复杂任务 | 10-60 秒 / 单文件 |
| **成本** | 高（按复杂度） | 极低（按 token 量） |

### 1.2 本项目的能力需求热力图

```
能力维度              需要度    Pro胜任   Flash胜任
────────────────────  ────────  ────────  ────────
Rust trait/泛型设计     ██████   ✅        ⚠️ 受限
状态机/LIFO栈逻辑       █████    ✅        ⚠️ 受限
DZ 语法解析器           █████    ✅        ❌
架构接口设计             ████     ✅        ❌
React 组件编写           ████     ⚠️ 可用   ✅
TypeScript DTO/interface ███      ✅        ✅
JSON 数据生成             ███      ✅        ✅
测试用例编写             ████     ✅        ✅
文档撰写                 ██       ✅        ✅
批量重复操作             ██       ⚠️ 浪费   ✅
```

### 1.3 推荐策略：Pro 掌舵，Flash 划桨

> **Pro 负责"对"的部分，Flash 负责"多"的部分。**
>
> Pro 产出架构和核心逻辑，Flash 在此基础上做规模扩展和重复劳动。
> 不是二选一，是每个阶段配置正确的人（模型）做正确的事。

## 三、模型使用策略

### 3.1 Pro 的使用规则

```
适用场景：
  ✅ 首次定义接口签名（任何 Port trait）
  ✅ 涉及 Rust 所有权/生命周期的结构设计
  ✅ 状态机逻辑（战场模块、效果栈、结算引擎）
  ✅ DZ 解析器（lexer + parser + validator）
  ✅ 涉及多个 Port 协调的编排逻辑
  ✅ 安全相关的代码（AI 产出校验、文件系统错误恢复）

不适用场景：
  ❌ 重复性的文件创建（同一个模式写 N 个文件）
  ❌ JSON 数据生成（配比表、测试数据）
  ❌ 已知模板的代码（React 组件、TypeScript interface）
  ❌ 文档撰写
```

### 3.2 Flash 的使用规则

```
适用场景：
  ✅ Pro 已产出 1-2 个示范文件后，Flash 批量补齐剩余
  ✅ TypeScript 端的所有 Port 接口定义
  ✅ React 组件的 JSX 渲染层
  ✅ 测试用例（给定输入→预期输出已明确）
  ✅ 文档（README、CHANGELOG、用户指南）
  ✅ CI 脚本、构建配置

使用前提：
  ⚠️ Flash 工作前，Pro 必须已经产出同类任务的 1 个示范文件
  ⚠️ 示范文件必须通过人工审查（保证方向正确）
  ⚠️ Flash 批量产出后，需全部通过 parser/compiler 校验
```

### 3.3 协作流程

```
1. Pro 产出架构设计和接口定义
     ↓ 人工审查通过
2. Pro 产出每个模块的 1 个示范文件
     ↓ 人工审查通过
3. Flash 基于示范文件批量产出同类代码
     ↓ 自动编译 + 测试
4. 编译失败的文件 → Pro 修复后 → Flash 参照重新生成
5. 全部通过 → 人工代码审查 → 合并
```

### 3.4 成本估算

```
Pro 调用 — 约 25 项核心任务，每项 1-3 轮对话：
  预估：75-100 轮 Pro 对话 → 中等成本

Flash 调用 — 约 17 项扩展任务，每项 1-2 轮对话：
  预估：25-35 轮 Flash 对话 → 极低成本

总成本比 = 约 7:3（Pro 占 70% 成本但只做 60% 的任务数）
但 Pro 不做的那 40% 任务数，如果没有 Pro 的示范文件，Flash 会出大量错误。
所以本质上 Pro 的成本是"杠杆"——用少量高成本任务撬动大量低成本高准确率产出。
```

## 四、实战建议

### 哪种情况用 Pro 但感觉浪费？

**没有这种情况。** 如果你觉得"这段代码 Flash 应该也能写"，那它就是 Flash 的工作。如果 Flash 写出来有 bug 需要反复修，那它本来就应该是 Pro 的工作——用 Pro 一次写对，比 Flash 写三遍再修两遍更省钱。

### 判断标准（做决定时问自己三句话）

1. **"这段代码如果写错了，会导致状态不一致 / 结算错误 / 安全漏洞吗？"** → Pro
2. **"这段代码是同一模式的第 N 次重复吗？"** → Flash
3. **"这段代码是我第一次设计这个模块的整体结构吗？"** → Pro

### 底线

**任何涉及游戏规则结算的代码（效果栈、支付→结算→连锁），只用 Pro。** 这是游戏的公平性基础，Flash 在这里犯错的代价是不可接受的。
